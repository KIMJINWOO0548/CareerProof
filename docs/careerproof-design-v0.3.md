**목표**는 국내 지원자가 문항별 답변을 편집하면서 “이 문장을 뒷받침하는 내 경험은 무엇인가”, “어느 버전을 제출할 것인가”를 직접 확인할 수 있게 하는 것이다. 첫 배포 대상은 단일 사용자 로컬 BYOK 웹앱이다.

## 1. 한 문항의 제출 경로

가상시스템즈의 장비 제어 소프트웨어 개발 직무에 지원하는 상황이다. 사용자는 공백 포함 500자 문항에서 구현 경험을 더 구체화하고자 한다.

| 사용자 조작 | 상태·데이터 변화 | 화면에서 확인할 결과 |
|---|---|---|
| 경력 자료의 “지연 120ms → 85ms”를 읽고 확인 | 사실 후보의 원본 위치와 사용자가 확인한 역할·기간·측정 단위를 원장 버전에 연결 | 사실 ID, 원문, 주체·측정 조건, 사용 문항 |
| 작성 루프 실행 | 현재 문항, 원장, 제한과 문체 기준을 스냅샷으로 고정. 클라우드 호출은 예산을 예약 | 사용할 근거·보낼 정보, 비용 상한, 현재 단계 |
| “35% 단축” 제안 도착 | G2가 수치 불일치를 기록. 차이 35ms, 감소율은 약 29.2% | 문제 문장, 근거 링크, 직전 추천본. 측정 기준이 모호하면 보강 질문 |
| 검증된 제안의 변경을 수락 | 현재 편집 기준에 변경을 적용한 새 사용자 리비전 생성. 부분 수락도 완성된 본문으로 재검증 | 편집본과 추천본의 버전, 수정 전후 문장, 새 분량 |
| 직접 편집 후 제출본 확정 | 선택한 리비전의 G1~G3와 원장 유효성을 다시 확인한 뒤 승인 포인터 갱신 | 내보내기 화면에 확정 리비전 ID와 해당 본문 표시 |
| 이후 다른 표현을 시험 | 새 편집 리비전 생성. 예전 확정본은 독립적으로 조회 | 수정 중인 문서와 내보낼 버전 식별. 근거 철회 시 확정본도 재검토 |

```mermaid

    In[프로필·공고 가져오기] --> Check[출처와 주체 확인]
    Check --> Facts[확인한 사실 원장]

    Approve --> Export[확정본 내보내기]
    Head --> Review[선택한 버전 심사]
```

## 2. 작성과 채점에서 사용하는 데이터

| 객체 | 최소 필드 | 유효 조건 |
|---|---|---|
| 출처 | 소유자·프로젝트, 출처 ID, 유형, 입력 버전·해시, JSON Pointer 또는 페이지·원문 범위 | 범위가 원문 안에 있고 같은 프로젝트에 속함. 원문 저장은 사용자가 선택한 보관 모드를 따름 |
| 사실 버전 | 사실 ID·버전, 확인 상태, 주체·역할, 행동, 대상, 기간, 결과, 단위, 출처 참조 | 팀 성과의 주체와 개인의 행동을 구분. 새 버전에서도 과거에 인용한 버전을 추적 가능 |
| 주장 | 리비전 ID, 문장 내 범위, 주장 유형, 자신이 의존하는 사실 ID·버전, 선택적 산식과 피연산자 | 하나의 문장 안에 “내가 수행”과 “팀 전체 달성”이 함께 있으면 두 주장으로 검증 |
| 회사 요구사항 | 브리프·공고 버전, 명시/추론, 필수/우대, 원문 위치, 정규화 용어 | 명시 요건은 원문에 연결. 회사가 원하는 기술을 사용자의 보유 기술로 자동 변환하지 않음 |
| 평가 입력 | 대상 범위, 리비전 목록, 브리프·루브릭 버전, 페르소나, 입력 범위, 모델 설정 | 실행 도중 편집본이 바뀌어도 보고서는 실행 시작 시 선택한 버전에 연결 |

**사실 검토 예시.** “배치 지연을 35ms 줄였다”는 확인한 두 측정값의 차이로 검증할 수 있다. “혼자 아키텍처를 바꿔 35ms 줄였다”는 개인 역할과 원인에 대한 근거가 추가로 필요하다. 검토 화면은 확인이 필요한 구간을 선택하고 동일 출처에서 사실을 확인하거나 문구를 고치게 한다.

## 3. 문체 규칙과 분량 계산의 구현 기준

### 3.1 문체 진단 계약

Phase 1 초기 가중치는 형식 반복 30, 상투 표현 30, 구체성 결핍 40을 제안한다. 각 축 원점수는 0~1이고 총점은 가중합에 0.5를 더한 뒤 내림한 0~100 정수다. 화면의 축별 기여도에는 소수 한 자리까지 허용한다. G4는 표시된 정수 총점과 동점일 때의 구체성 결핍 원점수를 비교한다. 이 배분은 스모크셋 조정 대상이다.

| 축 | PoC 계산의 출발점 (제안값) | 해석을 제한하는 조건 |
|---|---|---|
| 형식 반복 | 인접한 세 문장의 동일 종결 패턴, 문두 접속사 반복, 유형별 기호 규칙을 검사한다. 연속 중복 매치를 하나의 규칙 구간으로 묶고, 신호가 있는 문장 수를 전체 분석 대상 문장 수로 나눈다. | 3문장 미만이면 3연속 패턴은 미적용. 경력기술서의 불릿·화살표는 기호 규칙에서 제외 |
| 상투 표현 | 사전 매치가 있는 문장 수 ÷ 전체 문장 수. 같은 문장에서 겹치는 표현은 가장 긴 매치를 우선해 한 번 계산 | 단어만 바꿔도 낮아질 수 있는 값이므로 G4가 별도 근거 개선을 요구 |
| 구체성 결핍 | 문항에 적용 가능한 요소(본인 행동, 역할, 제약·시행착오, 결과·검증) 중 확인된 근거로 연결되지 않은 요소 수 ÷ 적용 가능한 요소 수 | 지원 동기·미래 계획은 과거 실적과 별도 적용표 사용. 근거가 아직 확인되지 않으면 질문으로 표시 |

분모가 0이거나 문서 유형에 전체 지수가 적용되지 않으면 총점을 `null`로 반환한다. 길이 보류인 경우 관찰할 수 있는 축과 참고값을 제공하고 목표 도달 판정은 생략한다. 규칙별 결과에는 `rule_id`, 원문 범위, 매칭 설명, 해당 근거를 넣는다. 구체성 결핍처럼 특정 문장에 문자가 존재하지 않는 관찰은 문항 전체의 보강 질문으로 표시한다. 정적 UI의 간이 문체 숫자는 규칙 엔진의 평가 실측과 별도로 관리한다.

### 3.2 카운터 순서와 테스트 벡터

1. 입력 원문을 보존하고 CRLF를 단일 논리 줄바꿈으로 해석한다. 줄 수는 빈 입력에서 0, 그 외에는 논리 줄바꿈 개수 + 1이다.
2. 제출 프리셋에 정규화 방식이 명시된 경우에만 적용한다. Phase 1의 공백 제외 대상 기본값은 U+0020이다. 탭, NBSP 등 추가 제외 문자는 프리셋으로 지정한다.
3. 문자 카운터에서 공백 정책과 줄바꿈 정책을 적용한다. 일반 단위는 grapheme 또는 UTF-16이며 이모지에 별도 1자·2자 정책이 있으면 해당 grapheme에 그 값을 한 번 적용한다. 바이트 수는 지정 인코딩으로 처리한 실제 바이트 수다. 유효하지 않은 문자를 치환한 추정값으로 통과시키지 않는다. [Unicode 텍스트 분할 규칙](https://unicode.org/reports/tr29/)
4. 문자·바이트·줄 각각의 활성 제한과 비교한다. 제출 분량은 PII 복원 후 확인한다. 등록된 사이트 표시값과 다르면 사용자 보정 결과와 검증일을 프리셋 범위에 기록한다.

| 원문 | 적용 조건 | 결과 |
|---|---|---|
| 빈 문자열 | 제한만 검사 | 0자, 0바이트, 0줄. 답변 필수 검사는 별도로 실패 |
| `가 A\r\n나` | 공백 포함, 줄바꿈 1자와 LF 바이트, grapheme | 5자, UTF-8 9바이트, CP949 7바이트, 2줄 |
| `가 A\r\n나` | 위와 같고 줄바꿈 2자와 CRLF 바이트 | 6자, UTF-8 10바이트, CP949 8바이트, 2줄 |
| `가😀` | 이모지 2자 | 3자, UTF-8 7바이트, 1줄. CP949 제한이 걸리면 이모지 위치를 표시하고 G1 실패 |
| `가` (분해형 자모) | 원문 보존, grapheme, UTF-8 | 1자, 6바이트. NFC 적용을 명시한 프리셋은 1자, 3바이트 |
| `가\n` | 줄바꿈 문자 제거 | 1자, 2줄. 줄 수 제한은 원문의 마지막 빈 줄도 포함 |

## 4. 위원회 점수표와 보고서

각 단계의 이름은 L1=0%, L2=40%, L3=70%, L4=100%다. 적용 가능하지만 제출 자료에 근거가 없으면 L1이다. 회사 인재상·포트폴리오 등 평가에 필요한 자료 자체를 확보하지 못한 경우에는 `not_assessable`과 사유를 보낸다. 부분 소계에는 유효 최대 배점을 같이 표시한다. 전체 100점 총점은 15개 기준이 모두 평가 가능한 회차에만 제공한다.

| 페르소나·기준 | 배점 | L1 | L2 | L3 | L4 |
|---|---:|---|---|---|---|
| 실무 팀장 · 직무 요건 | 8 | 대응 근거 없음 | 기술 언급 | 핵심 요건과 본인 업무 연결 | 핵심 요건에 대응하는 역할·검증 결과 확인 |
| 실무 팀장 · 설계와 해결 | 8 | 과정 없음 | 문제만 설명 | 제약과 선택 설명 | 대안·선택 이유·검증 연결 |
| 실무 팀장 · 기술 정확성 | 4 | 핵심 설명 모순 | 용어만 열거 | 기술 간 관계를 정확히 설명 | 경계 조건·실패 조건까지 일관됨 |
| 실무 팀원 · 구현 구체성 | 8 | 행동 식별 불가 | 도구·역할 중 하나 | 본인 작업의 입력·출력 확인 | 역할 경계·실제 결과·출처 확인 |
| 실무 팀원 · 협업과 검증 | 7 | 협업·검증 근거 없음 | 활동 이름 언급 | 검토·테스트와 변경점 연결 | 재현 자료와 피드백 반영 결과 제시 |
| 실무 팀원 · 검증 가능성 | 5 | 핵심 주장과 근거 충돌 | 주체·조건이 불명확 | 핵심 주장의 주체와 근거 확인 | 성과 범위·한계·귀속까지 확인 |
| 인사 팀장 · 가치 정합 | 8 | 명시 가치와 충돌·연결 없음 | 가치 이름 반복 | 확인된 행동과 연결 | 맥락·행동·결과로 정합성 설명 |
| 인사 팀장 · 동기와 회사 특화 | 6 | 회사·직무 연결 없음 | 일반적 동기 | 공고의 구체 업무와 동기 연결 | 회사 근거와 본인 선택·기여를 함께 설명 |
| 인사 팀장 · 성장과 태도 | 4 | 관찰 가능한 예 없음 | 학습 의지만 언급 | 피드백과 행동 변화 | 변화가 다음 과업에 적용된 근거 |
| 인사 담당자 · 문항 의도 | 7 | 질문과 무관 | 질문 일부만 답함 | 핵심 질문을 모두 답함 | 답과 근거가 직접 연결됨 |
| 인사 담당자 · 가독성과 구조 | 6 | 핵심 주장 식별 곤란 | 결론 또는 사례만 명확 | 주장·사례 순서를 따라갈 수 있음 | 핵심 내용을 빠르게 찾고 근거까지 추적 가능 |
| 인사 담당자 · 형식과 분량 | 4 | 필수 문항 누락 | 일부 형식 제약 위반 | 지정된 필수 형식·분량 충족 | 최신 제출 규칙과 필수 항목 확인 완료 |
| 임원 · 비즈니스 임팩트 | 10 | 결과 근거 없음 | 개선 방향만 언급 | 사용자·운영 결과와 연결 | 기여 범위와 효과의 조건까지 확인 |
| 임원 · 1년 후 기여 | 8 | 시나리오 없음 | 일반 포부 | 직무에 맞는 행동 계획 | 시작 조건·협업·검증 기준까지 구체화 |
| 임원 · 학습 속도 | 7 | 근거 없음 | 배운 주제만 명시 | 시행착오와 적용 과정 확인 | 학습 전후 변화·재사용 근거 확인 |

**산술 예제.** 전 기준이 L3인 회차는 실무진 28.0, 인사팀 24.5, 임원진 17.5로 총 70.0점이다. 인사 팀장 검토 전체가 검증 실패하면 나머지는 57.4/82점이다. Fast는 유효 회차 1개로 표시한다. Deep은 완전한 회차가 둘 이상일 때 최소~최대 관측 범위와 중앙값을 함께 표시한다. 이 범위의 의미는 판정의 반복 변동이다.

Fast 모드에서는 5개 역할이 한 요청의 입력을 공유한다. 역할별로 읽을 자료 묶음을 표시해 평가를 유도한다. 역할 간 정보 접근을 실제로 제한해야 하는 블라인드 자료는 공통 입력에서 제거한다. Deep 모드는 각 역할에 허용한 자료만 독립 호출로 보낸다. 양쪽 모두 인용은 해당 역할에 제공한 문항·버전에서 검증한다.
