## 1. 제품 원칙과 사용자 흐름

- **사실 우선.** 지원자가 확인한 역할·성과·기술·수치에 근거해 작성한다. 공고는 요구사항의 출처이며 지원자 경험의 근거로 쓰지 않는다.
- **사용자 통제.** 문항별 편집, Pause → Edit → Resume, 전후 비교, 수정 제안 수락·거절, 명시적 최종 확정을 제공한다.
- **설명 가능한 진단.** 문체의 세 축과 근거 위치, 위원회 평가 범위와 변동 폭을 표시한다. 전 점수 화면에 “점수는 진단이며 합격 예측이 아닙니다”를 표시한다. 공고에 AI 활용 안내가 있으면 사용자가 확인할 수 있게 표시한다.
- **실행 비용과 개인정보.** 문체 규칙과 길이 계산은 LLM 호출 없이 실행한다. BYOK 호출과 외부 리서치의 대상과 전송 범위를 실행 전 알린다. 기본 작업은 로컬 메모리에 두며 로컬 저장은 사용자가 선택한다.
- **제품 흐름.** 프로필 입력 또는 가져오기 → 사실 확인 → 공고·문항 입력 → 초안 작성·제안 비교 → 문항 분량 확인 → 심사·캡처된 근거 확인 → 확정본 복사·내보내기. 위원회와 포트폴리오 갭 분석은 Phase 2에 연결한다.

## 3. 시스템 아키텍처

| 영역 | 책임 |
|---|---|
| `frontend/src/` | React·Zustand 기반 온보딩, 문항 탭, 카운터, 근거 패널, 전후 비교, 일시 정지·재개, 위원회 보고서. Phase 2 이후 Tracker. |
| `backend/app/domain/` | Pydantic v2 데이터 계약, `CountingRule`, `FactLedger`, `RunMachine`, 수용 게이트. |
| `backend/app/services/` | JSON Resume 가져오기, 문체 규칙, `WriterPolicy`, 포트폴리오 추출, 회사 브리프, 위원회. |
| `backend/app/core/` | `RunSecretStore`, `TokenBudgetGuard`, `QuotaContext`, `PIIRedactor`. |
| `backend/app/infra/` | FastAPI에서 사용하는 `LLMPort` 구현, SQLite 저장소, 이벤트 저장·재생. |
| `backend/eval/` | 문체·위원회 하네스와 선택 연구용 탐지기 실행. 연구용 모델·데이터는 기본 앱 이미지와 런타임 의존성에서 제외한다. |
| `extension/` | Phase 4 MV3 브리지와 채용 사이트별 입력 어댑터. |

- 1단계는 단일 백엔드 프로세스와 SQLite로 실행한다. 사용자 소유 레코드와 이벤트에는 `owner_id`를 두고, 로컬 기본값은 `local`을 사용한다. 접근 계층에서 소유자와 대상 ID를 함께 조회한다. 로컬 작업 본문 저장 정책은 §10을 따른다.
- `LLMPort`는 구조화 요청·응답, 제공자 오류 분류, 토큰 사용량을 노출한다. Phase 1은 클라우드 BYOK 제공자 1개와 로컬 Ollama 경로를 검증한다. LiteLLM SDK는 어댑터 뒤의 초기 구현 후보이며 버전과 공급망을 확인한 뒤 설치한다. 각 제공자의 스키마 출력·오류·사용량 동작은 계약 테스트로 확인한다. [LiteLLM 공식 문서](https://docs.litellm.ai/docs)
- `UnlimitedLocalQuota` 뒤에 `CreditLedgerQuota`를 붙일 수 있도록 포트를 유지한다. 인증, 작업 큐, 접근 통제, 데이터 분리와 과금은 §10의 전환 과제에 포함한다.

## 4. 데이터 모델과 가져오기

### 4.1 문서 유형

| `portfolio` | 문서 추출본과 저장소 증거 | 추출 미리보기·증거 대응 중심. 문체 표시가 있으면 참고로만 제공한다. |

### 4.2 `CandidateProfile`, `FactCandidate`, `FactLedger`

1. JSON Resume 파일을 크기 제한과 고정 로컬 스키마로 검사한다. 업로드의 `$schema`, 첨부 URL, 인라인 링크를 이용해 원격 파일을 가져오지 않는다.
2. 매핑 미리보기에서 `work` → 경력, `projects` → 프로젝트, `skills` → 기술, `education`·`certificates` → 학력·자격으로 보여 준다. `basics`의 연락처는 로컬 프로필에만 매핑하고 작성 입력에서는 가린다. 선택 필드 누락을 허용하며 미지원·매핑 불가 항목을 표시한다.
3. 가져온 경력·수치·기술은 원본 위치를 가진 `FactCandidate`로 표시한다. JSON은 JSON Pointer, PDF는 페이지와 범위, 직접 입력은 필드 또는 답변 ID를 출처로 기록한다. PDF, GitHub, LLM 추출본에도 동일한 확인 절차를 적용한다.
4. 사용자가 지원자와의 관계, 맡은 역할, 기간, 수치·단위·측정 기준을 확인한 후보만 `FactLedger`의 `user_verified=true` 사실로 저장한다. 문항별 `must_keep`는 확인된 사실과 함께 지정한다.

가상 예제

```json
{
  "fact_id": "F-007",
  "version": 1,
  "kind": "metric",
  "text": "가상 프로젝트에서 배치 처리 지연을 120ms에서 85ms로 단축",
  "structured": {"subject": "가상 프로젝트", "before": 120, "after": 85, "unit": "ms"},
  "source": {"type": "json_resume", "pointer": "/work/0/highlights/0"},
  "user_verified": true
}
```

확인·수정·철회 시 원장 버전을 갱신한다. 실행은 확인된 사실의 스냅샷을 참조한다. 철회된 사실을 사용한 기존 리비전은 손대지 않고 재검토 표시를 붙인다. 최종 확정·내보내기 시 현재 원장으로 다시 검증한다.

### 4.3 `ApplicationForm`, `QuestionDraft`, `Revision`

- `ApplicationForm`은 회사, 직무, 공고·브리프 ID, 프리셋, 문항으로 구성한다. 문항은 `kind`, 제목, `counting_rule_id`, `must_keep_fact_ids`, 편집 기준인 `head_revision_id`, 자동 제안의 `best_revision_id`, 확정본인 `approved_revision_id`를 가진다.
- `Revision`은 추가 전용이다. `revision_id`, `parent_id`, `source(user|ai)`, 텍스트 또는 구조화 본문, 원장·규칙 버전, 분량, 문체 점수, 주장별 근거, 게이트 결과를 저장한다. 문체 현재값은 지정된 리비전에서 조회한다. 자동 후보가 기각돼도 편집 기준은 그대로 유지한다.
- Phase 1 출력은 확정 답변 복사·TXT, CareerProof 자체 JSON 내보내기를 제공한다. 자체 JSON 포맷은 버전·필드·문항별 분량 제한과 리비전·원장 연결을 보존한다. 공유용 확정 답변과 로컬 전체 내보내기를 별도 버튼으로 제공해 사용자가 포함 범위를 확인한다. 자체 JSON 복원은 포맷 버전과 리비전·원장 참조를 검증한 후 사용자가 확인한다. JSON Resume는 프로필 가져오기 교환 계약이다.

## 5. 한국어 문체 진단

- `KoreanAIStyleScorer`는 0~100 문체 진단 지수와 축별 값, 규칙 버전, 원문 근거 구간, 신뢰도, `abstain`과 `calibrated`를 반환한다. 값이 높을수록 반복 표현, 상투성, 구체성 결핍을 점검할 필요가 크다.

| 축 | 진단 항목과 표시 |
|---|---|
| `pattern` | 문두·어미 반복, 유사한 문장 길이, 반복 문단 구조 및 문서 유형에 따른 기호 사용. `career_desc`에서 불릿·화살표 밀도를 감점에 사용하지 않는다. |
| `cliche` | 상투어·번역투 표현. `rules_ko.yaml`에 표현, 규칙 ID, 근거, 가중치를 두고 매칭된 구간을 표시한다. |
| `specificity_deficit` | 구체 행동, 역할, 측정값·단위, 기술, 제약·시행착오의 부족. 검증 가능한 원장 사실을 활용한 서술을 제안하며 수치 개수 자체를 개선 근거로 삼지 않는다. |

- 세 축의 가중 합으로 총점을 계산한다. `weights.yaml`에 축별 가중치, 규칙 버전, 적용 문서 유형을 기록한다. 초기에는 `calibrated=false`로 표시한다. 선택형 LLM 체크리스트는 이후 필요할 때 구체화 조언과 인용을 별도로 표시한다.
- NFC 정규화와 바깥 공백 제거 후 300 grapheme 미만(제안값)이면 `confidence=low`, `abstain=true`로 둔다. UI에 참고용 점수와 구체화 단서는 표시하고 목표 도달 조건은 건너뛴다. 사이트의 제출 분량 계산과 문체 분석 길이 기준은 독립적이다. [길이별 보정 연구](https://arxiv.org/abs/2611.10901)
- 근거 구간은 원문 기준 유니코드 코드 포인트의 반열린 범위 `[start, end)`로 전달한다. 프런트엔드는 UTF-16 위치로 변환하며 정규화 전후의 위치를 매핑한다.
- 사용자가 목표 점수를 선택했을 때에만 목표 종료를 적용한다. G1~G4를 통과한 유효 리비전에 대해 비교하며, 목표가 없어도 정체·횟수·예산으로 종료하거나 사실 보강을 요청할 수 있다.
- 참고 문서를 직접 제공한 경우 로컬 n-gram 중복 경고를 선택할 수 있다. 경고의 비교 범위는 그 문서들이다. 쉼표·띄어쓰기·품사 피처를 추가할 때는 기본 점수 변화와 문서 유형별 오탐을 따로 측정한다 (§11).

## 6. 사실 기반 작성과 상태 머신

### 6.1 `WriterPolicy`와 수용 게이트

작성 입력은 문항, 적용할 제한, 사용자가 확인한 원장 사실, 필요한 회사 브리프 근거로 구성한다. 출력은 수정안과 문장·필드별 주장 목록을 구조화한다. 각 주장에 본문 범위, `fact_refs[]`, 필요한 경우 구조화된 값·단위·기간·주체·역할 및 파생 식별자를 둔다. 화면에서 변경 전후와 근거를 보고 사용자가 수락하거나 거절할 수 있다.

| 게이트 | 검사 | 실패 시 |
|---|---|---|
| G1 분량 | PII 복원 후 `CountingRule`의 문자·바이트·줄 제한과 금지 문자 정책을 적용한다. | 축약 1회 후 불충족이면 자동 후보 기각. |
| G2 근거 | 참조 ID와 버전, 확인 상태, 실제 본문 주장 대응을 검사한다. 수치와 단위, 경력 기간, 고유명사, 업무·팀 성과의 귀속 등을 확인한다. | 잘못된 대응은 후보 기각. 연속 두 번 실패하거나 의미 검증이 불확실하면 `needs_user_input`으로 일시 정지한다. |
| G3 보존 | 해당 문항의 `must_keep` 사실이 의미와 주체를 유지한 채 모두 포함됐는지 검증한다. | 자동 후보 기각. 사용자가 의도적으로 바꾼 경우 원장·문항 설정을 갱신한 뒤 다시 검증한다. |
| G4 개선 | 초안에 구체 행동·제약·결과 등 확인 가능한 개선이 있는지 먼저 확인한다. 두 점수 모두 보류 상태가 아니고 같은 규칙 버전이면 문체 총점이 직전 best 이하일 때 승격을 검토하며, 동점은 구체성 결핍이 낮아야 한다. 점수 보류 또는 적용 제외 시에는 완성도·근거 개선을 검토한다. | 직전 best 유지. 단순 기호 삭제나 점수 변화만으로 승격하지 않는다. |

- `fact_refs[]`에 실제 ID가 들어 있어도 문장별 주체·수치·역할이 불일치하면 실패한다. 예를 들어 120ms → 85ms는 35ms 감소이고, 허용 산식과 반올림 규칙을 적용한 경우 약 29.2% 감소다. 원장 입력과 다른 35% 감소 또는 팀 성과를 개인 단독 성과로 바꾼 문장은 기각한다.
- 파생 사실은 사전 정의한 계산 유형에 한해 코드에서 값·분모·단위·반올림을 재계산한다. 자유 서술에서 코드로 검증하기 어려운 비교·인과·성과 귀속은 사용자 검토로 보낸다. 자동 검증이 일반 자연어의 사실성을 보장한다는 표현을 사용하지 않는다.
- 초기 본문은 G1~G3 검증 후 첫 best가 될 수 있다. 첫 후보의 G4 기준은 원장 근거와 문항 적합성을 갖추는 것이다. 문체 보류 상태에서도 근거·분량·보존 검증은 수행한다. 직전 유효본이 없으면 종료 시 최종 리비전은 비워 둔다.
- 사용자가 수동 편집하면 새 `source=user` 리비전을 만들고 재검증한다. 편집본과 best를 화면에서 구분하고, 확정은 현재 원장·제한으로 재검증된 선택본에만 반영한다. 원장·분량 규칙이 바뀌면 기존 best를 재검증하고 실패 시 best 지정을 해제한다. 문체 규칙 버전이 바뀌면 비교 대상을 새 규칙으로 다시 계산한다.

### 6.2 전이표

전이표의 실행 가능한 표현을 `run_machine.py`에 두고 동일 데이터에서 전이 테스트를 생성한다. `RUNNING`의 하위 단계는 `WRITE → SCORE → DECIDE`다. 최초 사용자 원문도 점검하며 필요 시 `WRITE`에서 생성한다.

| 현재 | 조건·명령 | 다음 및 처리 |
|---|---|---|
| `IDLE` | `start` | `RUNNING.WRITE`. 규칙·원장·예산·목표 스냅샷과 실행 생성. |
| `WRITE` | G1~G3 통과 | `SCORE`. 후보 리비전 추가. |
| `WRITE` | 게이트 재시도 소진 | `DECIDE`. 기각 기록과 직전 best 유지. G2 불확실 또는 연속 실패는 `PAUSED(needs_user_input)`. |
| `SCORE` | 진단 완료 | `DECIDE`. 점수 및 신뢰도 반영. |
| `DECIDE` | G4 평가 | 승격 여부 결정 후 아래 종료 조건을 순서대로 평가. |
| `DECIDE` | 유효 best, 목표 설정, `abstain=false`, 점수 ≤ 목표 | `COMPLETED(target_reached)`. |
| `DECIDE` | 수행 횟수 ≥ `max_iter` | `COMPLETED(max_iter)`. |
| `DECIDE` | 정체 연속 2회, 구체성 보강 필요 (제안값) | `PAUSED(needs_user_input)`. 원인·측정 기준·역할 등 근거 질문 최대 3개. |
| `DECIDE` | 정체 연속 2회, 그 외 (제안값) | `COMPLETED(stagnated)`. 기본 기준은 자동 승격 실패 또는 비교 가능한 유효 점수의 2점 미만 개선이다. 보류·적용 제외 시에는 근거·완성도 개선 여부를 사용한다. |
| `DECIDE` | 그 외 | `WRITE`. 다음 반복 실행. |
| `RUNNING.*` | `pause` | `PAUSING → PAUSED(user)`. 현재 단계 결과를 원자적으로 반영한 뒤 정지. |
| `RUNNING.*`, `PAUSING` | 사용자 중단 | `COMPLETED(user_stop)`. 진행 중 결과를 폐기하고 마지막 best를 반환. |
| `RUNNING.*` | 예산 부족, 키 오류·만료, 재시도 소진 | `PAUSED`로 전이하며 각각 `budget_limit`, `key_required`, `provider_error`를 기록한다. 429·5xx·타임아웃은 횟수와 예산을 제한하여 백오프 재시도. |
| `RUNNING.*`, `PAUSING` | 비복구 오류 | `FAILED`. 오류 코드를 저장하고 중단. |
| `PAUSED(*)` | `resume(base_revision_id, command_id)` | 최신 편집 기준과 비교. 입력과 키가 준비되면 편집분을 새 리비전으로 추가하고 `RUNNING.SCORE`. 수정분이 없으면 저장된 체크포인트에서 재개. |
| `PAUSED(needs_user_input)` | `answer_questions` | 제안 사실을 만들고 사용자 확인이 끝나면 스냅샷을 갱신하여 `RUNNING.WRITE`. |
| `PAUSED(*)` 또는 실행 중 | `cancel` | `CANCELLED`. 진행 중 응답을 중단 또는 폐기하며 사용량 정산은 보존. |
| `COMPLETED` | `edit` 또는 `rescore` | `COMPLETED`. 새 리비전을 검증·재측정. |
| `COMPLETED` | `continue_loop` 또는 `recommittee` | 새 작성 Run 또는 별도 위원회 Run 생성. |
| 서버 기동 | 이전 `RUNNING` 또는 `PAUSING` 실행 발견 | `PAUSED`. 메모리 작업은 `input_required`, 저장 작업의 클라우드 실행은 `key_required`, 저장 작업의 Ollama 실행은 사용자 재개 대기. |

불변식

1. 편집 본문은 `PAUSED` 또는 `COMPLETED`에서만 갱신한다.
2. 추가 전용 리비전과 부모 연결을 일관되게 유지한다.
3. 자동 완료 본문은 게이트를 통과한 best 리비전에서 읽는다. 최종 사용자 선택은 별도 확정한다.
4. 영속 이벤트 `seq`는 실행별 결번 없이 증가한다. 이벤트와 그에 대응하는 상태 변경을 같은 저장 트랜잭션에서 기록한다.
5. 커맨드는 `(owner_id, run_id, command_id)` 기준으로 멱등하다. 동일 ID에 다른 요청 본문을 사용하거나 `base_revision_id`가 최신 편집 기준과 다르면 409를 반환한다.
6. 예상 상한을 확보한 후에만 호출한다. 진행 중 호출은 예산 예약에 포함한다. 실사용량을 확인할 수 없으면 추가 호출을 중지하고 사용량 미확인 상태를 표시한다.
7. 취소된 실행이나 이전 체크포인트의 뒤늦은 응답은 상태·리비전을 갱신하지 못한다.

### 6.3 이벤트와 BYOK 전달

- 클라우드 BYOK 실행은 `POST /runs`의 `X-LLM-API-Key`로 키를 전달한다. 서버는 프로세스 메모리의 TTL 저장소에 실행 키를 두고, 실행에 한정된 별도 `run_token`을 반환한다. `GET /runs/{id}/events`는 `fetch`의 `Authorization: Bearer <run_token>` 헤더로 SSE를 연다. [EventSource API](https://developer.mozilla.org/en-US/docs/Web/API/EventSource/EventSource) · [fetch 기반 SSE 참고 구현](https://github.com/Azure/fetch-event-source)
- 새로고침·재연결은 같은 브라우저 세션에서 해당 로컬 작업에 다시 접근해 실행 토큰을 갱신하고 `Last-Event-ID` 이후를 재생한다. 오래된 토큰은 실행·소유자가 일치해도 만료를 적용한다. 커맨드는 별도 POST로 처리한다.

| 영속 이벤트 | 주요 필드 |
|---|---|
| `run_state` | 상태, 이유 코드 |
| `iteration_start` | 반복 번호, 최대 횟수 |
| `revision_created` | 리비전 ID, 부모 ID, 작성 주체, 길이 |
| `ai_score_result` | 총점, 세 축, 신뢰도, 보류 여부, 근거 조회 ID |
| `gate_rejected`, `needs_user_input` | 게이트, 이유 코드, 후보 또는 질문 조회 ID |
| `budget_update`, `error` | 사용·예약액 또는 오류 코드와 재시도 가능 여부 |
| `completed` | 확정 후보 ID, 점수, 종료 이유, 목표 도달 여부 |

연결 유지를 위한 heartbeat는 SSE 주석으로 전송한다. 질문 문장·인용·개인정보·키는 이벤트에 싣지 않는다. 현재 실행에서 접근 가능한 본문은 별도의 소유자 접근으로 조회한다 (§10).

## 7. 멀티 페르소나 심사

### 7.1 범위, 배점, 정보 입력

지원서 단위 평가는 전체 문항과 포트폴리오, 갭 분석으로 100점 루브릭을 적용한다. 문항 단위는 해당 문항과 해당하는 기준 및 브리프에 한정하고, 적용 배점에 대한 비율을 참고로 표시한다. 문체 진단 지수는 위원회 채점 입력에서 제외한다.

| 그룹 | 페르소나 | 기준과 배점 | 합계 | 주요 입력 |
|---|---|---|---:|---|
| 실무진 | 실무 팀장 | 직무 요건 충족(8), 설계·트러블슈팅 깊이(8), 기술 정확성(4) | 20 | 문항, 명시 JD 요건, 포트폴리오·GitHub 증거 |

그룹별 배점은 실무진 40점, 인사팀 35점, 임원진 25점이다.

### 7.2 실행·검증

- 각 기준의 4단계 앵커(0%, 40%, 70%, 100%)를 루브릭 데이터로 정의한다. 모델은 단계 ID를 선택하고 코드가 환산·합산한다. 기준별 소수점은 보존하고 UI 단계에서 반올림한다.
- **Fast**는 단일 호출로 5개 페르소나의 검토를 반환한다. **Deep**은 각 페르소나를 독립 호출하고 루브릭 선택지 제시 순서를 교차하여 3회(제안값) 평가한다. 같은 회차의 검토가 모두 유효하면 회차별 총점을 만든 뒤 중앙값·최솟값·최댓값을 산출한다.
- JSON 스키마 확인 → 원문 인용 확인 → 기준·근거 참조 검증 → 코드 합산 순서로 처리한다. 정규화된 인용이 원문의 부분문자열이어야 하며 원문 위치로 역매핑해 하이라이트한다. 일치 지점이 여러 개라면 원본 문항·범위 식별자로 확인한다. 잘못된 응답은 최대 2회 재시도한다.
- 재시도 후에도 유효하지 않은 페르소나는 누락 사유와 함께 표시한다. 불완전 회차는 `earned_points / valid_max_points`로 부분 소계를 보여 준다. 전체 척도의 총점·범위는 5개 페르소나를 모두 포함한 유효 회차로 계산한다. 적용 기준이 없는 문항 평가는 보류한다.
- 보고서는 평가 범위, 유효 표본 수, 점수와 범위, 페르소나별 기준, 검증된 인용, 감점 사유 및 수정안, 명시 요건과 연결된 갭, 노력 대비 준비 액션을 제공한다. 범위 폭이 10점 이상이면 “평가 변동 큼”을 표시한다(제안값).
- 작성·심사 모델 분리를 권장하고 동일 계열이면 안내한다. 블라인드 입력에서 평가하고, 분량 자체에 가산하지 않도록 프롬프트와 테스트에 반영한다. [LLM 판사 연구](https://arxiv.org/abs/2306.05685) · [채용 자기선호 실험](https://arxiv.org/abs/2509.00462)
- **선택 Phase 2.5.** 날조 위험이나 근거가 부족한 문장에서 페르소나별 면접 꼬리질문을 최대 2개 생성하고, 준비해야 할 증거를 알려 준다.

## 8. 회사·포트폴리오 리서치

### 8.1 `CompanyBrief`

| 우선도 | 출처 | 처리 |
|---|---|---|
| S0 | 사용자가 붙여넣은 공고·문항 | 원문에 인용 위치를 연결한다. 이미지 공고는 텍스트 붙여넣기를 기본으로 하고 로컬 OCR은 선택이다. |
| S1 | OpenDART 공시 | 기업 개황·공시용 공식 참조. 인증과 공시 데이터가 있는 기업에서 사용한다. [OpenDART](https://opendart.fss.or.kr/) |
| S2 | 기업 공식 사이트·채용 페이지·보도자료 | 사용자 트리거로 조회한다. 이용 조건과 robots.txt, 호출 간격, 허용 URL·리다이렉트 범위를 확인한다. |
| S3 | 공개 웹 검색 요약 | 출처가 확인된 경우 낮은 신뢰도의 참고 자료로 사용한다. |

- `CompanyBrief.claims[]`에 ID, `explicit|inferred|unverified`, 분류, 문장, 신뢰도, 출처와 조회 시각을 둔다. 공고는 `text_hash`와 원문 범위, 외부 문서는 URL과 짧은 인용문으로 추적한다. JD 커버리지·위원회 갭은 `explicit` 요구사항을 기본 근거로 삼는다.
- 캐시는 `(owner_id, 정규화 회사명, 정규화 직무, 공고 해시)`로 분리한다. 기본 TTL 7일(제안값)과 공고 마감 중 더 이른 시점에 만료한다. DART 데이터는 소스별 TTL을 둘 수 있다. 기본 메모리 모드에서는 공고나 공고 유래 브리프를 영구 캐시에 넣지 않는다.
- 공고 수집은 사용자 제공 자료 중심으로 운용한다. 채용 플랫폼 대량 크롤링은 제품 범위에서 제외한다. 법적 판단이 필요한 신규 수집 경로는 실제 사용할 때 별도로 검토한다.

### 8.2 JD 요구사항과 포트폴리오

- **결정적 JD 매칭.** 명시 요건에서 추출한 용어를 한국어·영문 기술 동의어와 경계 규칙으로 정규화한다. 예를 들어 C++과 `cpp`를 잇고, C와 C++은 별개로 판정한다. 확인된 행동·성과·코드 증거가 있으면 `covered`, 언급만 있으면 `weak`, 발견하지 못하면 `missing`으로 반환한다. 이 값은 공고 대비 제출 자료의 커버리지다.
- **추출 미리보기.** Phase 2 첫 범위는 PDF·Markdown이고 DOCX를 다음 후보로 둔다. 같은 화면에서 추출 텍스트·페이지·읽기 순서를 확인하고 열·표·이미지 누락 가능성을 표시한다. HWP/HWPX와 이미지 OCR은 선택 기능이며 샘플 정확도와 라이선스를 검증한 후 연결한다.
- **GitHub 신호.** 사용자가 지정한 공개 레포에서 README(목적·실행·구조·한계), 테스트와 언어, CI 파일·실행, 활동, 라이선스·릴리스를 점검한다. 각 신호에 0~10점, 증거 링크, 확인 시각을 연결하고 접근 제한·관측 실패를 낮은 점수와 구분한다. 공개 저장소 활동만으로 사용자 개인의 기여를 확정하지 않는다. [OpenSSF Scorecard](https://github.com/ossf/scorecard)
- **갭 → 준비 액션.** `priority = (요건 중요도 × 갭 크기) / 노력`을 사용하고 노력은 S=1, M=2, L=4로 둔다(제안값). 액션에는 할 일, 기대 증거, 공고 요건 ID를 붙인다. 수행 여부는 사용자가 사실 원장에서 확인한다.

## 9. 한국 채용 사이트 대응

### 9.1 `CountingRule`과 보정

```json
{
  "rule_id": "rule_q1",
  "char_unit": "grapheme",
  "include_spaces": true,
  "newline": "count_1",
  "emoji_policy": "count_2",
  "byte_encoding": "cp949",
  "max_chars": 1000,
  "max_bytes": null,
  "max_lines": null,
  "verified": null
}
```

- 문자 단위는 grapheme 또는 UTF-16, 줄바꿈은 `count_1|count_2|strip`, 이모지 처리는 `count_1|count_2|forbid`, 바이트 인코딩은 UTF-8 또는 CP949를 지원한다. 에디터와 백엔드는 동일한 샘플로 검증한다. 원본을 보존하며 문자·바이트 계산용 정규화는 프리셋에 명시할 때 적용한다.
- CR·LF·CRLF를 논리적 줄바꿈으로 인식한다. 문자·바이트 계산에는 설정된 줄바꿈 변환을 적용한다. 줄 수 제한은 원문의 논리적 줄 수로 계산한다. 바이트 제한이 설정된 경우 해당 인코딩으로 표현할 수 없는 문자 위치를 보여 주고, 사용자 확인·수정 후 다시 계산한다.
- 문자·바이트·줄 제한을 각각 집계하고 가장 높은 사용률 구간을 표시한다. 90%부터 주황, 100% 초과 또는 인코딩·이모지 위반은 빨강이다. 한도에 정확히 맞는 입력은 G1에서 통과한다.
- 사이트의 표시값으로 규칙 후보를 보정한다. 줄바꿈, 결합형 한글, 공백, 이모지가 포함된 복수 테스트 문자열을 제공하고 사이트 숫자를 입력받는다. 여러 규칙이 여전히 일치하면 구분용 샘플을 더 제안하며 자동 확정하지 않는다. 스마트 따옴표·제로폭 문자 등의 정제는 전후 미리보기를 거친다.
- `recruiter`, `greeting`, `saramin`, `jobkorea`, `wanted`, `custom` 프리셋은 데이터 파일로 관리한다. 확인한 규칙과 적용 범위, 날짜, 방법을 저장하고 미검증 프리셋에 표시한다.

### 9.2 문항 파서와 답변 재사용

- 붙여넣은 공고에서 문항 경계와 “1,000자 이내”, “880바이트·11줄 이내” 같은 제한을 결정적 규칙으로 추출한다. 애매한 경우 사용자 수정 또는 BYOK LLM 폴백 후 확인을 거친다.
- 지원 동기, 직무 역량, 협업, 실패 경험, 입사 후 포부 등 유형별 구조 가이드를 제공한다. 유형은 편집을 돕는 설정이며 문항 문구·제한을 고칠 수 있다.
- **선택 Phase 2.5.** Answer Bank에서 마스터 답변의 근거와 부모 리비전을 유지하며 회사별 파생본을 만든다. Tracker에서 회사·마감·상태를 확인한다.

### 9.3 Chrome 확장 브리지

- MV3의 기본 흐름은 작업 화면에서 선택한 확정 텍스트 → 웹앱 content script의 `window.postMessage` 수신 → extension runtime → 사용자가 허가한 채용 사이트 content script다. 데이터는 대상 문항, 확정본, 규칙 ID 등 필요한 필드만 포함한다. [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)
- 송신·수신 오리진, 발신 창, 버전과 메시지 스키마를 검사한다. 사용자 트리거와 허용 대상 탭을 결합하며, Bridge 메시지와 확장 저장소로 BYOK 키·실행 토큰·프로필 전체를 보내지 않는다.
- JSON 가져오기·내보내기를 폴백으로 유지한다. localhost 직접 호출은 해당 Chrome 버전의 Local Network Access 및 실제 대상 오리진을 검증한 뒤 선택할 수 있다. [Chrome LNA](https://developer.chrome.com/blog/local-network-access)
- 사이트별 DOM 어댑터는 사용자가 부여한 최소 호스트 권한을 사용한다. SPA 필드를 탐지하고 제어 입력의 native setter와 이벤트가 사이트 상태에 반영되는지 실측한다. 입력 뒤 사이트 표시값을 재확인하여 불일치를 안내한다. 사람의 확인과 제출로 흐름을 끝낸다.

| Run·SSE | SQLite에 실행·상태·이벤트 메타데이터와 점수·사용량을 저장. | 동일 이벤트 계약. 본문은 권한을 갖는 별도 조회로 제공. |
| API 키, PII 매핑 | 실행에 한정한 프로세스 메모리, TTL과 작업 종료 정리. | 동일 정책. |

- 메모리 프로젝트는 서버 재시작 후 작업 본문 복원이 가능한 CareerProof JSON을 사용자가 다시 가져올 때 새 Run을 시작할 수 있다. 세션에 남은 메타데이터에는 재첨부가 필요하다고 표시한다. 로컬 저장 프로젝트는 마지막 체크포인트의 문서·원장 버전을 기준으로 키 재입력 또는 로컬 실행 재개를 안내한다.
- `X-LLM-API-Key`, `Authorization`, 사용자 파일명과 본문을 애플리케이션·미들웨어·제공자 디버그 및 오류 로그에서 제외한다. 키 또는 본문을 URL과 브라우저 영구 저장소에 넣지 않는다.
- Docker Compose는 `127.0.0.1` 바인딩을 기본으로 한다. 브라우저 요청의 Host·Origin 및 로컬 세션을 확인하고 쓰기 요청을 보호한다. 외부 분석·텔레메트리는 기본 배포에 포함하지 않는다. 사용자 전체 삭제는 저장된 원장·원본·초안·Run·이벤트·캐시와 메모리 작업을 함께 처리한다.

### 10.2 비용 제한

- 입력 토큰과 최대 출력 토큰, 재시도 및 예정 호출 수를 표시한다. `pricing.yaml`은 모델, 단가, 통화, 적용일(`as_of`)을 관리한다. 클라우드 가격이 불명확하면 비용 미확인을 표시하고 해당 모델로 비용 상한이 설정된 실행을 시작하지 않는다.
- 클라우드 요청 전에 보수적 최대 비용을 예약하고 제공자 사용량을 확보하면 정산한다. 상한을 감당할 수 없으면 호출하지 않고 `PAUSED(budget_limit)`로 전이한다. 사용량이 누락된 실행은 미확인 상태로 남기고 추가 호출을 보류한다. 제공자 청구 내역과 내부 예상액의 차이는 실측에서 기록한다.
- Ollama 실행은 호출당 시간제한과 Run 전체 시간 예산을 둔다. 비용 표시는 API 사용료 범위로 한정한다.

### 10.3 `PIIRedactor`와 모델 호출

- 제공자 호출 전 이름·연락처·이메일·주민번호 패턴·주소·생년월일을 가역 플레이스홀더로 치환한다. 블라인드 평가는 사진, 성별, 나이, 출신지, 가족관계도 입력에서 제거한다. 사용자가 전송 예정 필드를 확인할 수 있게 한다.
- 작성 응답에서는 예약된 플레이스홀더만 현재 실행의 매핑으로 복원한 뒤 G1 분량을 검사한다. 알 수 없는 토큰과 불완전한 매핑은 검토 대상으로 처리한다. 심사 인용은 마스킹된 입력을 기준으로 검증하고 화면의 원문 위치로 매핑한다.
- 문서·공고는 프롬프트의 데이터 영역에 넣는다. 제공자에 도구·임의 네트워크 권한을 부여하지 않고, 구조화 출력 검증, 호출별 timeout·max_tokens와 재시도 제한을 적용한다.

## 11. 평가와 완료 기준

### 11.1 제품 문체·작성 하네스

- Phase 1 구현 전에 공개 권리가 확인된 가상 또는 익명화 자료로 20~30문항(제안값)의 스모크셋을 구성한다. 문서 유형, 짧은 응답, 반복·상투어, 사실만 보강한 쌍, 고유명사와 수치 변조, 한글·영문 기술 혼용, 경력기술서 불릿을 포함한다.
- 문체 진단은 반복 실행의 결정성, 사람이 확인한 상투어·구체성 구간과 하이라이트의 대응, 설명 가능성, 문서 유형에 맞는 규칙 적용을 측정한다. 작성은 수치·역할·기간 보존, 분량 성공률, 잘못 연결한 사실 참조 기각, 사용자가 확정한 변경을 측정한다.
- 일반 표현을 확인된 행동·제약으로 구체화한 쌍에서 진단이 개선되고, 기호·쉼표만 편집한 쌍이 근거 개선으로 승격되지 않는지 확인한다. 자동 합격·불합격을 만드는 점수로 평가하지 않는다.

### 11.2 선택 저작 기원 탐지 연구

- `backend/eval/`의 로컬 CLI에서만 실행한다. 참가자 동의·익명화·재사용 권리와 라벨 출처를 기록한다. 사람 작성, AI 첨삭, AI 생성의 세 흐름을 구분하고 같은 작성자·지원서·원문·파생본을 한 데이터 분할에 묶는다. 일부 직무와 생성 모델을 별도 홀드아웃에 남긴다. [KoLing 평가 설계](https://arxiv.org/abs/2610.22940) · [RAID](https://aclanthology.org/2024.acl-long.674/)
- Phase 2.5 이후 정식 비교의 초기 목표는 사람 작성 200문항, AI 생성 200문항과 별도 AI 첨삭 묶음이다(제안값). 임계값을 개발셋에서 정하고, 평가셋에서 길이 `<300`, `300–599`, `600–1000`, `>1000`와 문서 종류별 표본 수·보류율·커버리지, FPR·TPR 및 95% 신뢰구간을 공개한다. AUROC, 낮은 FPR의 TPR, 보정 곡선은 표본 수가 뒷받침하는 범위에서 보고한다.
- 쉼표, 띄어쓰기, 형태소 품사 피처를 제거한 비교 실험과 혼합 작성 평가를 한다. 미리 정한 개선량을 홀드아웃에서 충족하고 사람 글 오탐과 보류율이 악화되지 않으며 모델 가중치 접근·비용·재현성 조건을 충족할 때 추가 연구 피처로 유지한다. 제품 문체 진단 보정에는 사용자 관점의 글 품질 라벨을 사용한다.
- 출처, 집계 단위, 버전, 모델·프롬프트, 날짜, 길이 구간, 표본 수, 보류 정책을 리포트에 기록한다. 20~30문항 결과나 타 논문 수치는 한국어 자소서 탐지 성능 주장에 사용하지 않는다.
