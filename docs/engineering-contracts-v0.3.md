# CareerProof v0.3 구현 계약

**상태 · SPECIFIED**

**기준 ·** [CareerProof 상세 설계서 v0.2.2](careerproof-design-v0.2.2.md) §3–6, §10–12

[v0.3 제품 기준과 시연 기록](careerproof-design-v0.3.md) · [UI 상호작용 명세](ui-spec-v0.3.md)

Phase 1의 구현 경계를 API, 데이터, 상태 전이, 비용 정산과 인수 테스트 단위로 정의한다. 예시 ID, 토큰, 가격과 본문은 가상 데이터다. 경로와 상태 코드는 제안 계약이며 실행 결과는 구현 후 측정한다.

## 1. 실행 경계와 데이터 소유권

- React 앱과 FastAPI를 동일 로컬 오리진의 앱 셸에서 제공한다. 개발 모드도 프런트엔드 프록시를 사용해 브라우저에 보이는 오리진을 하나로 유지한다. Compose는 호스트의 `127.0.0.1`에만 공개한다. FastAPI, 작성 워커, 메모리 작업·키 저장소는 한 프로세스에서 실행한다.
- 사용자가 허용된 로컬 화면을 열면 서버가 브라우저 세션을 발급한다. 세션은 `HttpOnly`·`SameSite=Strict`의 호스트 한정 쿠키를 사용하고, 쓰기 요청은 정확한 `Origin`과 세션에 연결된 `X-CSRF-Token`을 확인한다. 설정된 `Host`만 받는다. 세션 식별자 원문은 쿠키에만 두고, 보관하는 세션 레코드는 무작위 식별자의 다이제스트·만료·폐기 정보를 사용한다. 소프트웨어가 HTTPS로 제공되면 쿠키에 `Secure`를 적용한다.
- `owner_id`는 세션을 조회하는 의존성에서 결정한다. HTTP 요청의 사용자 입력에서 가져오지 않는다. 로컬 단계의 기본 소유자는 `local`이다. 동일한 로컬 설치를 공유하는 OS 사용자를 서로 격리하는 모델은 Phase 5의 계정 인증과 테넌트 분리에서 다룬다.
- DB 읽기·갱신은 `(owner_id, target_id)`로 제한한다. Run, 문항, 리비전, 사실은 요청자가 같은 소유자이며 동일 작업에 속한 경우만 연결한다. 브라우저 상태에는 선택된 프로젝트와 실행 커서만 별도로 관리할 수 있고, 본문·키·실행 토큰을 웹 스토리지에 저장하지 않는다.

## 2. HTTP API와 SSE

| 실행 범위 | 경로 | 계약 |
|---|---|---|
| 세션 | `POST /session` | 앱 셸의 최초 요청에서 로컬 세션을 발급하거나 기존 세션을 확인한다. 이 초기 요청은 설정된 Host와 정확한 Origin을 검증한 후 후속 쓰기용 CSRF 값을 반환한다. 캐시를 사용하지 않는다. |
| 프로젝트·가져오기 | `POST /projects`, `POST /projects/{project_id}/imports` | 기본 저장 유형은 `memory`. 업로드 파싱 결과는 미리보기 ID와 후보로 반환한다. 세션과 작업에 연결된 후보를 확인할 수 있다. |
| 사실 | `POST /projects/{project_id}/facts/confirm` | 현재 `ledger_version`과 확인한 후보를 받아 새 버전을 생성한다. 수동 신규 사실에도 같은 확인 동작을 사용한다. |
| 수동 편집·확정 | `POST /questions/{question_id}/edits`, `POST /questions/{question_id}/approve` | 현재 문항에 대해 CAS를 적용한다. 편집은 새 리비전을 추가한다. 확정은 선택 리비전을 현재 원장과 분량 규칙으로 재검증한다. 실행 중인 문항은 일시 정지 후 요청할 수 있다. |
| 실행 생성 | `POST /runs` | `command_id`, 문항·편집 기준, 모델·예산·반복 한도·선택 목표를 받는다. 클라우드 키는 `X-LLM-API-Key`에서만 받는다. Ollama는 이 헤더가 필요 없다. |
| 실행 조회 | `GET /runs/{run_id}` | 소유자 세션으로 조회한다. `state`, `step`, `reason`, `prerequisites`, `head_revision_id`, `best_revision_id`, `last_seq` 및 비용 상태를 반환한다. 존재하지 않거나 소유 관계가 일치하지 않는 실행에는 `404`. |
| 스트림 토큰 | `POST /runs/{run_id}/stream-token` | 소유자 세션과 CSRF 검증 후 현재 실행에 한정된 새 토큰을 내준다. 새로고침 이후 또는 권한 유효기간이 끝났을 때 사용한다. |
| 명령 | `POST /runs/{run_id}/commands` | `pause`, `resume`, `stop`, `cancel`, `answer_questions`, `continue_loop`를 `kind`로 구분한다. 모든 명령은 `command_id`를 받는다. Phase 2의 `recommittee`는 독립 심사 실행을 생성한다. |
| 이벤트 | `GET /runs/{run_id}/events` | 로컬 세션과 `Authorization: Bearer <run_token>`으로 접근한다. 클라이언트는 `fetch` 기반 수신기를 사용한다. |
| 본문·질문 | `GET /questions/{question_id}/revisions/{revision_id}`, `GET /runs/{run_id}/questions` | 본문과 질문은 별도 소유자 조회에서 제공한다. 메모리 본문이 소실된 경우 `409 input_required`. 캐시에는 저장하지 않는다. |
| 삭제 | `DELETE /projects/{project_id}` | 권한과 CSRF 확인 후 작업의 실행·메타데이터·본문을 §6의 순서로 삭제한다. 전체 삭제는 현재 로컬 소유자가 관리하는 프로젝트와 관련 캐시에 같은 절차를 적용한다. |

실행 생성 예시

```http
POST /runs HTTP/1.1
Content-Type: application/json
X-CSRF-Token: <local-session-csrf>
X-LLM-API-Key: <ephemeral-byok-key>
```

```json
{
  "command_id": "a5786069-bf7d-48b9-aef4-60bc734a1aad",
  "question_id": "q_01",
  "base_revision_id": "rev_01",
  "provider_config_id": "cloud_default",
  "budget_limit_usd": "0.10",
  "max_iter": 3,
  "target_style_score": null
}
```

```json
{
  "run_id": "run_01",
  "state": "RUNNING",
  "step": "WRITE",
  "last_seq": 1,
  "run_token": "<ephemeral-stream-token>"
}
```

`max_iter`는 설정된 허용 범위 안의 양의 정수, 목표는 0–100 정수 또는 `null`, 비용 상한은 양의 십진 USD 문자열이다. 클라우드 실행 생성 시 허용 모델의 가격과 요청 키가 필요하다. 서버가 받은 키의 유효성은 제공자 응답에서 확인한다.

실행 생성 응답은 이미 저장된 결과의 시점을 반영한다. 응답을 잃은 탭이 같은 `command_id`를 재전송하면 기존 실행 ID로 응답한다. 재전송으로 생성된 토큰은 접근 권한만 갱신하며 실행을 다시 시작하지 않는다. `POST /runs`로 설정한 키가 재시작으로 사라진 경우, 클라우드 제공자 키가 필요한 다음 `resume` 요청에서 `X-LLM-API-Key`를 다시 보낸다. 시작 명령 재전송으로 키를 교체하거나 일시 정지를 해제할 수 없다.

편집을 포함한 재개 예시

```json
{
  "kind": "resume",
  "command_id": "c6d9fb32-fc82-417d-a628-f81c4f3e95fd",
  "base_revision_id": "rev_04",
  "edit": {"text": "가상의 팀에서 장비별 재현 조건을 정리했습니다."}
}
```

| HTTP | 코드 예시 | 처리 |
|---:|---|---|
| 400 | `invalid_last_event_id` | SSE 커서는 0 이상 정수다. 누락은 0으로 시작한다. |
| 401 | `session_required`, `stream_token_expired` | 세션을 확인하거나 새 스트림 토큰을 발급받는다. 모델 제공자의 401/403은 별도의 실행 상태 `PAUSED(key_required)`로 전달한다. |
| 403 | `origin_forbidden`, `csrf_invalid` | 서버 요청 경계에서 거절한다. |
| 404 | `not_found` | 대상의 존재와 소유 일치 여부를 함께 처리한다. |
| 409 | `stale_revision`, `stale_ledger`, `command_conflict`, `invalid_transition`, `input_required`, `cursor_ahead`, `run_active` | 코드를 기준으로 현재 문항을 다시 조회하거나 재개 조건을 해결한다. `stale_revision`에는 같은 문항의 현재 `head_revision_id`를 포함한다. |
| 422 | `invalid_request`, `unsupported_document_shape`, `unknown_model_pricing`, `provider_key_required` | 허용된 입력 범위와 수정 가능한 필드명을 구조화해 반환한다. |

API 오류의 `detail`은 고정 오류 코드와 필요한 필드 이름으로 구성한다. 파서 입력, 모델 응답 원문, 파일 이름, 제공자 오류 본문은 오류 메시지에 반영하지 않는다.

### 2.1 SSE 재생 계약

실행 토큰은 무작위 불투명 값으로 생성하고 소유자·세션·Run과 연결한다. 프로세스 메모리에서 만료와 폐기를 추적한다. 토큰의 범위는 스트림 조회이며 명령·작업 본문 조회는 세션 계약을 따른다. 종료된 실행도 유효한 세션에서 토큰을 발급받아 이벤트를 다시 재생할 수 있다.

```http
GET /runs/run_01/events HTTP/1.1
Accept: text/event-stream
Authorization: Bearer <ephemeral-stream-token>
Last-Event-ID: 17
```

```text
id: 18
event: run_state
data: {"state":"PAUSED","reason":"needs_user_input"}

id: 19
event: needs_user_input
data: {"questions_ref":"question_set_03"}

: heartbeat
```

- 커서는 마지막으로 UI 상태에 반영한 이벤트 ID다. 클라이언트는 실행별 `seq` 중복을 무시하고 다음 연결에 마지막 ID를 보낸다. 재생은 `seq > cursor ORDER BY seq`다. 현재 실행의 `last_seq`보다 큰 커서는 `409 cursor_ahead`로 반환한다. 재연결은 새 스냅샷의 `last_seq` 또는 0에서 시작할 수 있다.
- 단일 API 인스턴스에서는 SQLite를 기준으로 마지막 커서 이후 데이터를 읽는다. 알림을 연결하더라도 이벤트 테이블을 다시 확인하고, 주기적 조회로 알림 경합과 누락을 흡수한다. SQLite 트랜잭션을 열린 스트림 수명 동안 유지하지 않는다.
- `heartbeat`는 주석이며 저장하거나 순번을 부여하지 않는다. 영속 이벤트는 형식별 필드 허용 목록을 사용한다. 사용자 문자열은 명세의 별도 본문 조회 경로에 둔다. 종료 뒤 미정산 호출이 있으면 예산 이벤트가 이어질 수 있다. UI는 실행 종료와 남은 사용량 정산 상태를 함께 표시한다.

## 3. SQLite, 리비전 포인터와 명령 멱등성

| 레코드 | 저장 정책과 제약 |
|---|---|
| `runs` | 메타데이터. 상태·이유·다음 체크포인트·세대 번호 `generation`·스냅샷 버전·비용 상태·`last_seq`. 작업 본문에는 `workspace_mode` 정책을 적용한다. |
| `run_events` | 메타데이터. `(owner_id, run_id, seq)` 유일. 이벤트 종류별 허용 값과 출력 크기를 검증한다. |
| `command_receipts` | 대상 종류·대상 ID·`command_id` 범위의 유일 키, 정규화 요청 HMAC, 상태 코드, 리비전·실행 ID 등 결과 메타데이터. 헤더·본문·토큰 전문을 기록하지 않는다. |
| `provider_attempts` | `(owner_id, run_id, attempt_id)` 유일. 요청 예산·시간과 정산 상태, 확인된 사용량만 기록한다. 가격 정책 버전과 `generation`을 연결한다. |
| `question_heads` | `head_revision_id`(편집 기준), `best_revision_id`(자동 후보), `approved_revision_id`(승인본). 기본 메모리 프로젝트의 위치 데이터와 본문은 세션의 메모리 저장소에서 접근한다. |
| `revisions`, `revision_checks` | 리비전의 본문과 부모 ID는 불변. 분석 결과는 리비전·원장·분량·문체 규칙 버전에 연결된 추가 전용 검사 기록. 저장 옵션에 따라 메모리 또는 SQLite에 보관한다. |
| `fact_versions`, `sources`, `imports` | 원장 수정·철회는 새 버전 생성. 출처와 이전 리비전 참조는 해당 작업 안에서 유지한다. 업로드 파일 보관은 별도 사용자 옵션이다. |

### 3.1 세 포인터와 작성 기준

- 첫 입력과 사용자 편집은 `source=user` 리비전을 만든다. 생성한 리비전으로 `head_revision_id`를 갱신한다. 자동 제안을 편집창에 적용하면 현재 `head_revision_id`를 부모로 하는 새 사용자 리비전이 된다. 기각된 자동 결과는 편집 기준을 움직이지 않는다.
- 자동 승격은 `best_revision_id`만 갱신한다. 자동 반복의 `working_revision_id`는 해당 실행의 직전 승격본 또는 사용자가 재개할 때 지정한 검증된 편집본이다. 이전 자동 후보가 기각되면 실행의 작성 기준도 유지한다. 최신 편집의 의미 검증이 보류된 경우에는 기존 실행을 조용히 이어가기 전에 사용자 확인을 요청한다.
- `approved_revision_id`는 별도의 확정 명령으로 갱신한다. 사용자는 G1~G3를 현재 버전에서 통과한 편집본을 확정할 수 있다. G4는 자동 제안의 승격에 적용한다. 확정본과 자동 완료 후보를 UI에서 각각 확인할 수 있다.
- 원장 철회나 분량 규칙 변경 후에는 관련 결과를 재검증 상태로 표시한다. G1~G3 실패가 확인되면 best 지정을 해제한다. 이전 승인본은 참고 이력으로 보여 주며, 공유용 출력을 하기 전 현재 버전에서 검증한다. 문체 규칙이 바뀌면 비교 상대를 같은 규칙으로 다시 점수화한다.

### 3.2 쓰기 순서와 동시성

1. 세션·대상 소유권과 요청 스키마를 검증한다. 동일 프로젝트의 메모리 쓰기와 실행 명령은 단일 프로세스에서 직렬화하고, SQLite 쓰기는 짧은 트랜잭션으로 묶는다. 클라우드·Ollama 호출 또는 네트워크 응답 대기는 이 경계 바깥에서 수행한다.
2. `(owner_id, scope, target_id, command_id)`로 영수증을 먼저 조회한다. 실행 생성의 범위는 문항, 실행 명령의 범위는 Run, 수동 편집·확정의 범위는 문항이다. `command_id`는 클라이언트가 생성하며 실제 시도 전체에 같은 값을 사용한다.
3. 같은 요청 지문이 있으면 이전 결과를 그대로 반환한다. 명령 종류, 대상과 정규화 JSON으로 지문을 구성하며, 키는 지문 계산에서 제외한다. 본문이 있는 명령은 무작위 브라우저 세션 비밀을 키로 하는 HMAC을 저장한다. 비밀은 쿠키에 있고 DB에는 세션 다이제스트만 남는다. 다른 세션이 우연히 같은 ID를 보내거나 동일 세션이 본문을 바꾸면 `409 command_conflict`를 반환한다.
4. 이전 기록이 없으면 상태와 현재 편집 기준을 비교한다. 편집·재개·확정·새 실행 생성·계속 쓰기 요청의 `base_revision_id`는 현재 문항의 `head_revision_id`와 일치해야 한다. 문항에 편집본이 없는 경우 두 값이 `null`일 때만 시작한다. 원장 확인의 `ledger_version`도 동일한 방식으로 비교한다. `409`를 해결한 새 의도에는 새 `command_id`를 사용한다.
5. 상태 변경, 활성 실행의 세대, 로컬 저장 리비전·검증 정보, 이벤트와 영수증을 한 커밋에 기록한다. `last_seq`를 트랜잭션 안에서 증가시킨 뒤 해당 순번에 이벤트를 추가한다. 첫 이벤트는 1이다. 커밋 전 장애가 발생하면 이벤트와 영수증을 포함해 함께 롤백한다. 인증과 스키마를 통과한 명령이 상태 충돌로 거절된 경우에는 동일 요청의 재전송을 위해 오류 영수증을 기록한다.
6. 메모리 프로젝트에서 리비전이나 본문이 바뀌면 쓰기 잠금 안에서 새 상태를 미리 구성한다. 메타데이터 커밋 뒤 같은 잠금에서 메모리 객체를 교체하고, 그다음 UI 알림이나 다음 단계 실행을 예약한다. 데이터 조회도 같은 잠금에서 일관된 상태를 얻는다. 프로세스가 중간에 사라진 경우 다음 기동 시 `input_required` 복구 규칙을 적용한다.

**경합 결과.** 같은 탭의 네트워크 재전송은 리비전과 이벤트를 하나만 만든다. 두 탭이 서로 다른 ID로 같은 편집 기준을 변경하면 첫 번째 커밋 후 두 번째 요청이 `409 stale_revision`을 받는다. 동일 문항에는 `RUNNING`·`PAUSING` 또는 복구 가능한 `PAUSED` 작성 Run을 하나만 둔다. 작업 본문이 소실돼 `PAUSED(input_required)`로 복구했다면 편집권을 해제한다. 새 Run은 복원된 문항에 만들 수 있다. 정지를 요청한 탭과 완료가 경합하면 커밋 순서가 결과를 결정한다.

## 4. 작성 단계, 게이트와 전이

| 단계 | 검증과 전이 |
|---|---|
| 최초 기준본 | 시작 시 본문이 있으면 G1~G3 검사와 결정적 문체 계산을 먼저 수행한다. 검증된 기준본은 첫 best가 될 수 있다. 사용자가 선택한 유효 목표에 이미 닿으면 클라우드 호출 없이 `target_reached`로 완료한다. |
| `WRITE` | 새 반복에 들어갈 때 `iteration_start`를 기록한다. 제공자 응답의 구조를 검사하고 PII 플레이스홀더를 복원한다. 본문 범위와 주장의 연결을 복원된 본문 기준으로 변환한다. G1~G3를 검사하고 통과한 후보를 새 리비전으로 추가한다. |
| `SCORE` | 후보 또는 편집 기준에 문체 버전과 문서 유형을 적용한다. 점수·근거 범위·`abstain`을 검사 레코드로 남긴다. `resume_form`처럼 점수가 적용되지 않는 형식은 문체 결과를 비워 둔다. |
| `DECIDE` | G4로 승격 여부를 판정한 뒤 목표 도달 → 최대 반복 → 근거 질문이 필요한 정체 → 기타 정체 → 다음 반복 순으로 판정한다. 한 번의 전이에서 승격, 상태, 이벤트를 함께 반영한다. |

- **G1.** PII 복원 완료 후 문자·바이트·줄 제한을 각각 검사한다. 구체적인 초과량을 편집기에 표시한다. 자동 축약 재시도는 반복당 1회다. CP949 인코딩 오류와 금지 이모지를 분량과 함께 검사한다. 한도와 정확히 같으면 통과한다.
- **G2.** 모델이 제공한 주장 범위와 참조 ID를 검사하고, 독립된 로컬 규칙으로 원문 내 수치·단위·기간 표기와 구조화 필드를 확인한다. 사실의 주체·역할·수치·단위·관계 및 사실 버전을 대조한다. 예를 들어 `120ms → 85ms`에서 `35ms` 차이와 허용한 산식의 `29.2%`를 구별한다. 본문에 등록되지 않은 검증 대상이 있거나 자유 서술의 의미 대응을 확신하기 어려우면 사용자가 확인한다. 연속 두 번 근거 검증이 실패하거나 의미 해석이 불확실하면 `PAUSED(needs_user_input)`로 이동한다.
- **G3.** 현재 문항의 `must_keep_fact_ids`를 지원자 역할과 함께 보존한다. 표현이 달라져도 의미를 확인할 수 있어야 한다. 강제로 생략하려면 사용자가 필수 사실 설정을 변경한 뒤 같은 정책으로 재검증한다.
- **G4.** 첫 best는 G1~G3와 문항 적합성을 확인한다. 이후에는 구체 행동·역할·제약·결과 등의 유효한 개선이 필요하다. 비교 가능한 문체 값에서 새 총점이 직전 best를 넘으면 승격하지 않으며, 동점은 구체성 결핍이 낮아야 한다. 보류 또는 적용 제외는 근거와 구조화 필드 완성도를 사용한다. 이력이 없거나 유효 후보가 없으면 자동 완료 결과의 리비전 ID는 `null`일 수 있다.
- `max_iter`는 작성 반복 횟수이고 개별 호출 수와 별도로 집계한다. G1 축약, 첫 G2 오류 교정, 구조화 파싱과 전송의 재시도 각각에 한도를 둔다. 기본 제안은 반복당 G1·G2 교정 각 1회, 구조화 오류 재시도 최대 2회, 제공자 재시도 최대 2회다. 예산 추정과 실제 반복에서는 이 한도를 함께 적용한다. 구조화 오류와 게이트 기록은 요약 코드로 저장하고 입력 본문은 §6을 따른다.
- 정체는 자동 승격 실패 또는 비교 가능한 유효 점수가 2점 미만 개선된 경우를 연속 2회 누적한다(제안값). 점수 보류나 미적용 상황에서는 유효한 근거·완성도 개선을 기준으로 사용한다. 목표 도달 판정은 `target_style_score`가 명시적으로 있고 best가 현재 유효하며 `abstain=false`일 때만 적용한다.

### 4.1 일시 정지·정지·취소와 늦은 응답

| 명령·상황 | 상태와 결과 |
|---|---|
| `pause` | `RUNNING → PAUSING` 후 진행 중인 한 단계를 반영하고 `PAUSED`로 이동한다. 제공자 응답을 기다리는 중에는 사용자에게 대기 상태를 보여 준다. 단계가 끝난 뒤 다음 호출을 예약하지 않는다. 키·예산 등 다음 실행 조건이 사라졌다면 해당 조건을 함께 표시한다. |
| `resume` | `PAUSED`에서만 허용한다. 편집이 있으면 CAS 후 새 리비전을 만들고 `SCORE` 단계에서 다시 검증한다. 필요한 키·입력·예산 조건의 처리 여부를 먼저 확인한다. `budget_limit` 재개는 사용자가 화면에서 확인한 새 상한을 요청에 함께 보낼 수 있다. 미정산 사용량의 사유는 함께 남는다. 편집 없이 재개하면 마지막 완료 단계 다음부터 진행한다. |
| `answer_questions` | 최신 질문 묶음 ID, 현재 `ledger_version`과 사용자가 확인한 답변을 받는다. 확인된 사실만 새 원장 버전에 추가한다. 실행 스냅샷을 갱신하고 `WRITE`로 돌아간다. 필요한 질문에 답하지 않은 경우 일부 응답을 보관하더라도 일시 정지 상태를 유지한다. |
| `stop` | `RUNNING` 또는 `PAUSING`에서 마지막 유효 best로 `COMPLETED(user_stop)`. 실행 세대를 올린다. |
| `cancel` | 활성 또는 일시 정지 실행을 `CANCELLED`로 전이하고 실행 세대를 올린다. 가능한 경우 백엔드 호출을 취소한다. 이미 발생한 제공자 사용량은 정산 대상이다. |
| `continue_loop` | 완료된 실행에서 별도의 작성 Run을 생성한다. 현재 head, 원장과 규칙 버전을 새 실행에 스냅샷으로 기록한다. |

외부 호출 전에 `(run_id, generation, attempt_id)`를 캡처한다. 응답 처리 시 이 식별자와 기대 체크포인트를 현재 실행과 비교한다. `PAUSING`에서 해당 단계를 마무리할 때만 이미 진행 중인 같은 세대의 결과를 반영할 수 있다. 세대가 바뀐 응답은 리비전·best·`run_state`를 수정할 수 없으며, 신뢰할 수 있는 사용량은 해당 `attempt_id`에 한 번 정산한다. 브라우저 SSE 연결을 끊는 동작은 서버의 작성 워커에 명령을 보내지 않는다.

공유 원장이나 문항 규칙이 외부 호출을 기다리는 동안 바뀌면 워커는 이전 스냅샷의 결과를 현재 best 또는 승인본으로 승격하지 않는다. 호출 사용량은 정산하고 실행을 `PAUSED(needs_user_input)`로 옮겨 갱신된 설정을 표시한다. 사용자가 새 기준을 확인해 재개하면 그 기준으로 작성 입력을 다시 만든다.

## 5. 비용 예약, 오류와 복구

### 5.1 호출 예약·정산

1. 제공자·모델 설정을 고정 목록에서 선택해 Run에 스냅샷으로 저장한다. 클라우드 모델은 버전·통화·입력/출력 단가·적용일이 확인된 가격표를 사용한다. 입력 토큰 보수 추정과 `max_tokens`를 기준으로 가능한 최대 호출 비용을 구하고 소수 USD를 정수 최소 단위로 올림한다. 캐시 할인이나 무료 예약량을 기대 비용을 낮추는 근거로 사용하지 않는다.
2. 외부 호출 전에 `확정 사용액 + 미정산 예약액 + 다음 호출 예약액 ≤ 비용 상한`을 원자적으로 검사한다. 새 `attempt_id`와 예약 상태 `reserved`를 저장한다. 호출자가 외부 전송을 시작하기 직전 `dispatching`을 커밋한다. 대기 중에는 같은 Run의 작성 호출을 새로 발행하지 않는다. 상한 부족 시 `PAUSED(budget_limit)`을 기록한다.
3. 권위 있는 사용량이 오면 해당 예약을 해제하고 확정액을 합산한다. 실제 모델 계량·공급자 가격이 스냅샷과 다르면 격차를 기록하고 즉시 추가 호출을 멈춘다. 비용 상한은 제공자 청구 연동의 검증 결과와 함께 보고한다.
4. 명확한 무과금 실패는 예약을 해제할 수 있다. 타임아웃, 응답 손실, 서버 재시작 등 실제 사용량이 모호한 경우에는 예약을 `unknown` 상태로 유지한다. 추가 호출을 보류하며 응답·서비스 근거로 정산 가능할 때만 해제한다. 새로고침이나 예산 증액으로 미확인 예약이 사라지지 않는다.
5. Ollama 경로는 API 사용료를 0으로 표시하고 호출 시간제한과 실행 전체 시간 예산으로 제어한다. 정지·취소 후에 종료되지 않은 백엔드 프로세스 호출은 실패 상태로 관측하고 타임아웃이 지난 뒤 정리한다.

| 오류 | 분류와 상태 |
|---|---|
| 제공자 401/403 또는 TTL 만료 | 현재 실행 키를 폐기하고 `PAUSED(key_required)`. 권위 있는 무과금 응답은 예약 정산에 사용한다. |
| 429/5xx/타임아웃 | 새 예약이 가능하고 이전 호출의 과금 상태를 확인한 경우 횟수 제한·지수 백오프로 재시도한다. `Retry-After`가 있으면 남은 실행 시간 한도 안에서 적용한다. 재시도 소진 또는 사용량 미확인은 `PAUSED(provider_error)`로 이동한다. 미확인 사용량을 `prerequisites`에 표시한다. |
| 구조 검증 오류 | 응답의 내용을 그대로 기록하지 않고 스키마 오류 코드를 저장한다. 재시도는 예산과 별도 횟수 제한을 따른다. 게이트 실패는 §4의 분기 조건을 적용한다. |
| 저장소 불일치·비복구 오류 | 실행 결과를 반영할 수 없으면 `FAILED`. 사라진 프로세스에서 실패 상태를 커밋하지 못한 경우 다음 기동의 체크포인트 복구 절차를 따른다. |

### 5.2 기동 시 복구

- 워커를 시작하기 전에 이전 `RUNNING`·`PAUSING`을 조사하고 일시 정지 이벤트를 새 순번에 기록한다. `reserved` 상태에만 남은 호출은 발송 단계에 도달하지 않았으므로 예약을 해제할 수 있다. `dispatching` 중 끊긴 호출은 사용량을 확인할 때까지 보류한다. 재시작 전의 키·실행 토큰·PII 매핑은 프로세스와 함께 만료된다.
- 기본 메모리 프로젝트는 메타데이터 타임라인만 복구한다. `input_required`를 표시하고 사용자가 갖고 있는 CareerProof JSON을 가져오면 새 Run을 만들 수 있다. 이전 실행에 본문을 덧붙여 이어가는 동작은 범위 밖이다. 이미 종료된 메타데이터의 종료 이유는 유지한다.
- 로컬 저장 프로젝트에서 클라우드 실행을 재개하려면 마지막 체크포인트의 `key_required`를 해결한다. 로컬 Ollama 작업은 사용자의 `resume`을 기다린다. 이전 질문 답변과 미확인 예약 등 다른 재개 조건은 함께 유지한다. 새 제공자 요청 전에 연결한 원장·문항 버전을 재검증하고 PII 매핑을 다시 만든다.
- HTTP 응답을 보낸 뒤 커맨드 실행 예약 전에 프로세스가 사라지는 경우에도 위 복구 규칙을 적용한다. 실행 스케줄러는 커밋된 활성 상태에서 재개 가능한 체크포인트만 처리한다.

## 6. 개인정보와 로컬 저장·삭제

| 구분 | 기본 메모리 작업 | 로컬 저장을 선택한 작업 |
|---|---|---|
| 사용자 본문 | 프로필·문항·원장·리비전·근거·업로드 파싱본은 프로세스 메모리에서 처리한다. | 정규화 본문과 추적에 필요한 출처 데이터를 로컬 SQLite에 보관한다. 업로드 파일 원본 보관은 사용자가 별도로 선택한다. |
| 시스템 메타데이터 | 실행 이벤트, 안전한 오류 코드, 비용 예약·확정액과 명령 영수증을 SQLite에 기록한다. | 같은 이벤트 정책을 따른다. 본문은 세션 검증이 있는 별도 경로로 조회한다. |
| 키와 PII 매핑 | Run에 묶인 메모리, TTL, 상태에 따른 정리. | 동일. |

- 업로드 처리는 요청 크기를 제한하고 허용된 입력을 인메모리 버퍼로 읽는다. 사용한 프레임워크의 multipart 파일 롤오버와 프록시 임시파일 동작을 테스트하고, Phase 1 JSON 가져오기는 필요 시 크기 제한이 있는 원시 JSON 경로를 제공한다. 업로드 이름과 파싱 오류 원문은 로그에 남기지 않는다.
- `PIIRedactor`가 키 사용 호출 직전에 외부 전송 입력을 처리한다. 사용자는 전송 대상과 마스킹 결과를 확인할 수 있다. 제공자에는 문서 데이터를 구분한 구조와 실행에 필요한 사실만 전달한다. 제공자 debug logger와 중간 라우터의 본문·헤더 캡처 동작을 검사한다.
- 작성 출력은 실행의 예약된 플레이스홀더만 복원하고, 알 수 없는 토큰이나 매핑 누락은 검토 대상으로 처리한다. 심사용 인용은 마스킹된 원문에서 일치 위치를 확인한 뒤 원본 위치로 매핑한다. 복원 원본 기준 유니코드 코드 포인트 범위를 UI에서 UTF-16 범위로 변환한다.
- 삭제는 먼저 실행을 중단하고 세대를 올린 뒤, 프로젝트의 로컬 레코드와 이벤트, 관련 브리프·파일, 메모리 본문, 키·토큰을 정리한다. 키·토큰은 성공 응답 전에 폐기한다. 실행 중 콜백은 삭제된 작업을 다시 만들 수 없다. SQLite 저널과 앱 관리 백업의 처리도 인수 테스트에 포함한다. 별도 앱 밖으로 내보낸 파일은 화면에서 내보낸 위치와 사용자 관리 대상임을 안내한다.
